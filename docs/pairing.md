# Manual device pairing

The Android app exchanges a one-time code through `POST /wp-json/prices/v1/pairing/exchange`. The request has `pairing_code`, `device_name`, `device_identifier` (`prices-android`), `app_version`, and `android_version`. Codes use the confirmed `0000-0000` format. The response provides `device_id`, `token_type` (`Bearer`), `device_token`, and `authentication_method` (`device_token`). Unknown response fields are tolerated.

The device token is held temporarily in application memory during pairing and is never rendered, added to UI state, passed in routes, or logged. After `GET /wp-json/prices/v1/auth/me` succeeds, Phase B writes the token through the Phase A secure storage boundary, writes separate non-sensitive paired-session metadata, and only then establishes the final in-memory session. A failure rolls back partial state and leaves the discovered connection intact.

The discovered DataStore record remains `Discovered`. On process restart, complete secure metadata and the encrypted token are restored only after `/auth/me` verification; Products is not opened before that verification succeeds. Temporary network failures preserve the persistent records for retry. Invalid or revoked sessions are cleared and return to pairing. Local Disconnect clears in-memory and persisted local session state without revoking a server device, while preserving the discovered connection. Change Store additionally clears the discovered connection. QR pairing remains deferred.

The backend returns `PAIRING_FAILED` for invalid, expired, and replayed codes, so the client presents one truthful combined message. `RATE_LIMITED`, `PAIRING_DISABLED`, `DEVICE_LIMIT_REACHED`, `PERMISSION_DENIED`, `AUTHENTICATION_REQUIRED`, and the common error envelope are mapped without using human-readable messages for logic.
